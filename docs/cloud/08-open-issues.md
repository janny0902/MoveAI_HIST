다른 문서의 `미해결` 상태를 모아 보는 곳이다. 내용은 복제하지 않고 링크한다.

## 데이터가 없어서 막힌 것

### OPEN-01 트럭 목적지 — 해소됨

~~Matching M2 경로 회랑은 현재 위치와 목적지가 둘 다 있어야 하는데 목적지를 채우는 경로가 없었다.~~

**해소** 촬영할 때 목적지를 지정할 수 있게 했다. 지정하지 않으면 **기본 목적지**(물류산업진흥재단,
서울 마포구 마포대로 34)로 설정한다. 기본값은 `vision-processor/config.py`의
`DEFAULT_DESTINATION_*` 변수이며 환경변수로 덮어쓸 수 있다.

남은 부분: 주소 **검색**은 Maps API 키가 있어야 동작한다([OPEN-02](#open-02-google-maps-api-키가-없다)).
키가 없어도 기본 목적지로는 정상 동작한다.

운행 배차 시스템 연동은 여전히 없다. 목적지는 기사가 촬영 때 직접 정하거나 기본값을 쓴다.

- 참조: [MAT-09](05-matching-processor.md#mat-09-트럭-위치목적지-의존)

### OPEN-02 카카오 REST API 키가 없다

지도는 카카오로 통일했다. 키 하나가 두 기능을 막고 있다.

| 기능 | 쓰는 API | 없을 때 동작 |
|---|---|---|
| 목적지 **주소 검색** | 카카오 Local (`dapi.kakao.com`) | `GET /v1/geocode`가 503. UI가 기본 목적지만 쓰도록 degrade |
| **우회시간** | 카카오모빌리티 길찾기 (`apis-navi.kakaomobility.com`) | 직선거리 추정. `route_source=HAVERSINE_FALLBACK`으로 표시 |

- **필요**
  1. [developers.kakao.com](https://developers.kakao.com)에서 앱 생성 후 REST API 키 발급
  2. 그 앱에서 **카카오맵(Local) 활성화**
  3. **카카오모빌리티 길찾기는 콘솔이 다르다.** [developers.kakaomobility.com](https://developers.kakaomobility.com)에서 별도 신청·활성화가 필요할 수 있다
  4. 두 `infra/config.sh`의 `ENV_VARS`에 `KAKAO_REST_API_KEY` 추가

- 같은 키를 두 서비스에 쓴다. 키는 서버에만 두고 브라우저에 노출하지 않는다
- **주의** 아직 키가 없어 두 연동 모두 **실제 호출로 검증되지 않았다.** 스키마는 공식 문서
  기준으로 구현했다
- 참조: [MAT-03](05-matching-processor.md#mat-03-경로-api-미구성과-실패를-구분한다), [VIS-10](04-vision-processor.md#vis-10-목적지-지정과-주소-검색)

- **재검토 조건** 해당 모델이 다시 배포 가능해지거나 변환된 SavedModel을 확보하면
- 참조: [MODEL-01](03-ai-models.md#model-01-jax-owl-vit-v2는-배포-경로가-없다)

### OPEN-06 품질 임계값을 실차 데이터로 다시 봐야 한다

depth outlier 항목을 넣으며 가중치를 9개로 재배분해 **같은 사진의 quality_score가 이전과 다르다.**
ACCEPT 0.70 / LIMITED 0.50이 여전히 적절한지 검증되지 않았다.

- 참조: [MODEL-10](03-ai-models.md#model-10-품질점수-가중치를-9개-항목으로-재배분했다)

### OPEN-07 정확도 검증이 없다

설계서 4.11대로 GT가 없다. 현재 값은 어떤 정확도도 보장하지 않는다.
`safety_factor` 0.70은 **실차 검증 전까지 올리지 않는다.**

## 검증되지 않은 것

### OPEN-10 실제 모바일 브라우저에서 촬영 흐름 미확인

프론트 배포·서빙, 런타임 설정 주입, upload-url 발급, Signed URL PUT, 결과 폴링까지는
curl로 확인했다. **실제 휴대폰에서 카메라를 띄워 찍는 경로는 확인하지 못했다.**

- 확인 필요: iOS Safari / Android Chrome의 `capture` 동작, `createImageBitmap` 호환성,
  EXIF 파싱이 실제 단말 사진에서 동작하는지, 위치 권한 흐름
- **`buildIntrinsics`가 실제로 값을 만드는지가 특히 중요하다.** 단말이 `FocalLengthIn35mmFilm`을
  안 넣으면 `null`이 되어 기본 화각으로 떨어지고 quality_score가 약 0.10 낮아진다

### OPEN-11 백엔드 로직에 자동화된 테스트가 없다

로컬에 Python이 없어 단위 테스트를 돌릴 수 없었다. 검증이 전부 배포 후 수동 확인이다.

- **필요** Python 3.11 설치 후 `geometry_lite`, `solver`, `geo`에 대한 테스트
- 참조: [ENV-06](01-environment.md#env-06-로컬에-실행-가능한-python이-없다)

### OPEN-12 GCS lifecycle이 결과 JSON도 지운다

원본과 결과가 같은 버킷에 있어 둘 다 7일 뒤 삭제된다. Firestore가 정본이라 치명적이지 않지만,
결과 사본을 오래 남기려면 버킷을 분리해야 한다(`RESULTS_BUCKET_NAME`이 이미 분리 가능하다).

- 참조: [GCP-04](02-gcp-infra.md#gcp-04-버킷-lifecycle-7일)

## 보안

### OPEN-13 CORS와 인증이 열려 있다

- 세 서비스 모두 `--allow-unauthenticated`
- 버킷 CORS origin이 `*`
- 백엔드 `CORS_ALLOW_ORIGINS`는 프론트 URL을 자동으로 넣지만, 못 찾으면 `*`로 떨어진다

시연용으로는 충분하나 운영 전에는 좁혀야 한다.
누구나 `upload-url`을 발급받아 버킷에 쓸 수 있는 상태다.

## 화면 목적 변경 이후 남은 것

### OPEN-14 장소명 지오코딩이 빈 결과를 준다

`GET /v1/geocode`에 `서울시청`, `부산역` 같은 **장소명**을 넣으면 `results: []`가 온다.
`서울`, 도로명 주소는 정상이다. 카카오 keyword 검색 쪽이 제대로 붙지 않는 것으로 보이는데
원인을 확인하지 않았다.

기준 위치를 주소로 옮기는 기능이 이 API를 쓴다. 지금은 빈 결과일 때 "주소를 찾지 못했습니다"가
뜨므로 화면이 죽지는 않지만, 장소명으로는 위치를 옮길 수 없다.

> 이전에는 이 응답을 **단일 객체로 받아** `lat`이 `undefined`가 된 채 렌더까지 흘러가
> `.toFixed()`에서 터졌고, 에러 바운더리가 없어 앱 전체가 흰 화면이 됐다. 배열로 받아
> 좌표가 숫자인 후보만 쓰도록 고쳤다. **에러 바운더리가 없다는 문제는 그대로다.**

### OPEN-15 적재율을 최대로 하면 건수가 준다

그리디가 부피당 무게(kg/CBM)가 낮은 것부터 담는다. 중량이 먼저 차는 구조에서 **적재율**을
최대로 하는 순서다. 그 결과 부피 큰 것 위주로 담겨 운송장 **건수**는 줄어든다
(같은 차에서 2,283건 40% → 259건 100%).

화면의 핵심 지표가 적재율이라 이렇게 맞췄다. "가능한 많은 운송장을 처리"가 목표라면
정렬 기준을 바꿔야 하고, 둘을 함께 보려면 목적함수에 가중치를 둬야 한다. **업무 규칙 확인 필요.**

---

### OPEN-16 후보 10만 건 조회가 50초 걸린다

Firestore에서 문서 10만 개를 읽는 시간이다. 타임아웃(900초) 안이라 동작하지만 체감이 느리고,
읽기 비용도 요청당 10만 건이다. 화면 기본값을 1만 건으로 둔 이유가 이것이다.

줄이려면 필요한 필드만 읽거나(`select()`), 터미널별로 미리 집계한 문서를 두어야 한다.

---

### OPEN-17 에러 바운더리가 없다

렌더 중 예외가 나면 앱 전체가 언마운트되어 **흰 화면**이 된다. OPEN-14에서 실제로 그렇게
됐고, 원인을 찾기 전까지는 "버튼을 눌렀는데 아무것도 안 나온다"로만 보였다.

React error boundary를 두고, 최소한 "화면을 그리지 못했습니다 + 새로고침" 정도는 남겨야 한다.

---

### OPEN-18 파렛트 적재 효율 0.85는 가정값이다

`PALLET_STACK_EFFICIENCY = 0.85`는 "규격이 제각각인 소포는 파렛트를 꽉 채우지 못한다"를
숫자 하나로 눌러 담은 값이고, 실측이 아니다. 파렛트 규격(1,100×1,100mm)과 깔판 높이(144mm)는
T-11 표준이라 근거가 있지만 이 계수는 없다.

실제 상차 데이터로 검증하거나 화주사 기준을 받아야 한다. **업무 규칙 확인 필요.**
