# 06. 프론트엔드 제약

React + Vite, nginx로 정적 서빙, **독립된 Cloud Run 서비스**다.

UI를 Stitch / AI Studio로 재생성할 때 지켜야 할 계약은
[frontend/UI_CONTRACT.md](../frontend/UI_CONTRACT.md)에 있다. 그 문서를 프롬프트에 붙여 넣는다.
여기에는 **배포·연동 쪽 제약**을 적는다.

> **화면의 목적이 바뀌었다.** 기사가 운행하며 사진을 찍는 앱이 아니라, **배차된 차에
> 물량을 얼마나 실을 수 있는지 관리자가 확인하는 화면**이다. 사진 경로와 목적지·운행 중
> 추적을 걷어냈다. FE-04·FE-08·FE-09·FE-10·FE-11·FE-15·FE-17은 사진 경로의 제약이라
> **현재 화면에서는 돌지 않는다** — 되돌릴 때를 위해 항목과 코드를 함께 남겨 둔다.
> 바뀐 흐름은 [FE-18](#fe-18-관리자용-적재-배정-화면)부터다.

### FE-01 왜 백엔드에서 분리했나

- **문제** 초기에는 vision-processor가 `/app`에서 PWA를 함께 서빙했다. UI를 한 줄 고쳐도 Depth 가중치를 굽는 Vision 이미지를 통째로 다시 빌드해 15분이 걸렸다.
- **대응** 별도 Cloud Run 서비스로 분리. 프론트 배포는 약 2분이고 백엔드를 건드리지 않는다.
- **대가** 교차 출처가 되어 백엔드에 CORS가 필요해졌다([FE-05](#fe-05-브라우저가-직접-호출하는-대상이-세-곳이다)).
- **상태** 적용됨. vision-processor의 `/app` 서빙과 `pwa/` 디렉터리는 제거했다

### FE-02 재생성 안전 경계

UI를 계속 생성 도구로 갈아끼울 것이므로, **재생성돼도 파이프라인이 깨지지 않도록** 디렉터리로
경계를 나눴다.

| 경로 | 성격 |
|---|---|
| `src/lib/` | **재생성 금지.** EXIF 파싱, 축소·focal 보정, 백엔드 계약, 흐름 제어 |
| `src/ui/`, `src/App.jsx`, `src/styles.css` | 교체 가능. 표현 계층 |

UI에서 `fetch`를 직접 부르지 않는다. `useAnalysis()` 훅 하나만 쓴다.
이 규칙이 지켜지면 UI를 몇 번을 갈아엎어도 백엔드 계약은 유지된다.

### FE-03 label과 input에 같은 id를 쓰면 버튼이 죽는다

- **증상** 촬영 버튼을 눌러도 아무 반응이 없다. 에러도 없다.
- **원인** `<label for="shootBtn" id="shootBtn">`과 `<input id="shootBtn">`이 id를 공유했다. `getElementById`는 문서 순서상 먼저 오는 label을 돌려주므로 `change` 핸들러가 input이 아니라 label에 붙었고, label의 `for`도 자기 자신을 가리켜 클릭이 input에 전달되지 않았다. 두 개가 겹친 문제다.
- **대응** React에서는 `useRef` + `ref.current.click()`으로 처리한다. id 결합을 아예 없앤다.
- **상태** 해소됨. 생성 도구가 만든 마크업에서 재발하기 쉬우니 UI_CONTRACT에도 적어 두었다

### FE-15 PC 카메라는 getUserMedia로 따로 열어야 한다

데스크톱 브라우저는 `<input capture="environment">`를 **무시하고** 그냥 파일 선택창을 연다.
"카메라로 촬영"을 눌렀는데 파일 탐색기가 뜨면 버그처럼 보이지만 표준 동작이다.

기기 판정(`navigator.maxTouchPoints > 0` + `pointer: coarse`)으로 갈라, 모바일은 OS
카메라를, PC는 `WebcamDialog`의 `getUserMedia` 미리보기를 띄운다. 캡처 결과는 `File`로
만들어 넘긴다 — 뒤쪽 파이프라인이 `File`을 받게 되어 있고 그 계약은 바꾸지 않는다.

웹캠 캡처에는 EXIF가 없어 초점거리가 기본값으로 추정된다. 모바일 촬영보다 정확도가
떨어지는 경로다.

### FE-17 사진은 한 번, 매칭은 계속

주변 화물은 계속 바뀌고 트럭이 움직이면 회랑도 같이 움직인다. 출발할 때 없던 화물이
도중에 잡히므로, 목적지에 닿을 때까지 주기적으로 다시 계산한다.

**사진을 다시 찍지는 않는다.** 상·하차를 하지 않는 한 빈 공간(CBM)은 그대로다. 첫 분석
결과를 그대로 재사용하고 위치만 갱신해 `POST /v1/match`를 다시 부른다. `event_id`는
매번 새로 발급한다 — matching이 그걸로 중복 처리를 막기 때문에(5.8) 재사용하면 두 번째
부터 무시된다.

멈추는 조건은 셋이다. 목적지 300m 이내 도착, 기사가 "추가 매칭 중단"을 누름, 새로 촬영.
GPS 오차가 100m대라 도착 반경을 그보다 넉넉히 잡았다. 중단 버튼이 필요한 이유는 하차
준비 중이거나 더 받을 생각이 없을 때 계속 추천이 뜨면 방해가 되기 때문이다.

주기는 시연용으로 1분이다. 실서비스에서는 더 길어야 한다 — 카카오 길찾기 호출이 후보
수에 비례한다.

**세션 복원** — 이 루프는 브라우저 안에서 돈다. 그래서 화면을 닫으면 추적이 끊기고
촬영 버튼만 남아 사진을 또 찍게 된다. 한 시간 안에 찍은 이력이 있으면
`GET /v1/trucks/{id}/session`으로 이어받고, 촬영 카드 대신 매칭 상태를 먼저 보여준다.

**상단 요약 띠** — 결론이 사진·지도·진행목록 아래에 있어서 운행 중에 매번 스크롤해야
했다. 실을 수 있나 / 몇 건 / 얼마나 남았나만 맨 위에 고정한다. 근거는 아래 결과 카드다.

### FE-16 고른 값은 다음 접속까지 남는다

기사는 같은 차로 하루에 여러 번 찍는다. 접속할 때마다 차량 번호와 목적지를 다시 고르게
하면 그 자체가 오입력 기회고, 차량 번호는 틀리면 결과가 통째로 어긋난다([VIS-11](04-vision-processor.md#vis-11-차량-제원이-곧-측정의-자다)).

`lib/prefs.js`가 localStorage에 남긴다. **기기의 선택**이지 서버가 알아야 할 상태가 아니라
여기 둔다 — 트럭의 실제 위치·적재중량 같은 업무 데이터는 Firestore가 정본이고 복제하지
않는다. 시크릿 모드처럼 저장소가 막힌 환경에서도 화면이 죽으면 안 되므로 모든 접근을 감쌌다.

차량은 `GET /v1/trucks` 목록에서 고른다. 자유 입력만 두면 등록되지 않은 번호를 넣고 왜
안 되는지 모른 채 막힌다. 목록에 없는 번호가 필요하면 "직접 입력"으로 돌아갈 수 있다.

### FE-04 카메라와 파일 선택을 분리한다

```html
<input type="file" accept="image/*" capture="environment" />  <!-- OS 기본 카메라 -->
<input type="file" accept="image/*" />                        <!-- 앨범·파일 -->
```

`capture`가 있으면 모바일에서 카메라가 바로 뜨고 갤러리를 못 고른다. 설계서 2.1이 지정한 것은
카메라 쪽이므로 그대로 두고, 이미 찍어 둔 사진으로 테스트할 수 있게 입력을 하나 더 뒀다.

처리 중에는 두 버튼을 비활성화하고, 끝나면 `input.value = ""`로 비운다.
비우지 않으면 같은 파일을 다시 골라도 `change`가 발생하지 않는다.

### FE-05 브라우저가 직접 호출하는 대상이 세 곳이다

서버를 경유하지 않으므로 각각 CORS가 열려 있어야 한다.

| 대상 | 용도 | 설정 위치 |
|---|---|---|
| vision-processor | upload-url 발급, 결과 조회 | `CORS_ALLOW_ORIGINS` 환경변수 |
| GCS Signed URL | 이미지 직접 PUT | 버킷 CORS([GCP-05](02-gcp-infra.md#gcp-05-브라우저-업로드에-버킷-cors가-필요하다)) |
| matching-processor | 결과 조회 | `CORS_ALLOW_ORIGINS` 환경변수 |

**프론트 주소가 바뀌면 백엔드 두 개를 다시 배포해야 한다.** 두 `infra/config.sh`가 `frontend`
서비스 URL을 자동으로 찾아 넣으므로, 프론트 배포 후 백엔드를 재배포하면 된다.

### FE-06 백엔드 주소를 빌드에 굽지 않는다

- **이유** 같은 이미지를 dev/prod 어디에나 올릴 수 있어야 하고, 백엔드 URL이 바뀌었다고 프론트를 다시 빌드하고 싶지 않다.
- **구현** 컨테이너 시작 시 `/docker-entrypoint.d/40-write-config.sh`가 환경변수를 읽어 `/usr/share/nginx/html/config.js`를 쓴다.

```js
window.__APP_CONFIG__ = { VISION_BASE_URL: "...", MATCHING_BASE_URL: "..." };
```

- `index.html`이 번들보다 먼저 `/config.js`를 로드한다.
- `config.js`와 `index.html`은 `Cache-Control: no-store`. 해시가 붙은 `/assets/`만 장기 캐시한다.
- 로컬 개발에서는 `public/config.js`를 직접 만든다(gitignore 대상).

### FE-07 nginx는 $PORT를 써야 한다

Cloud Run이 주입하는 포트로 listen하지 않으면 기동 확인에 실패한다.
`nginx:alpine`의 템플릿 기능(`/etc/nginx/templates/*.template` → envsubst)으로 `${PORT}`를 치환한다.

SPA 폴백(`try_files $uri $uri/ /index.html`)이 있어야 새로고침 시 404가 나지 않는다.

### FE-08 EXIF는 축소 전에 읽어야 한다

- **문제** canvas로 리사이즈하면 EXIF가 사라진다. 서버는 EXIF 없는 이미지를 받는다.
- **대응** 원본 `ArrayBuffer`에서 필요한 태그만 직접 파싱한다(Orientation 0x0112, FocalLength 0x920A, FocalLengthIn35mmFilm 0xA405). focal 태그는 대개 IFD0이 아니라 Exif SubIFD(0x8769)에 있다.
- **방향** EXIF orientation을 **픽셀에 굽는다.** 축소된 JPEG에는 방향 정보가 남지 않기 때문이다. 90/270도 회전이면 가로세로가 바뀌는 것에 주의한다.
- **적용 위치** `src/lib/exif.js`, `src/lib/image.js`

### FE-09 focal length를 리사이즈 배율로 보정해야 한다

**이 한 줄이 빠지면 depth unprojection이 배율만큼 통째로 어긋나고 그 오차가 CBM까지 간다.**

```js
const focalPxOriginal = exif.focal35 * (diagPx / FILM_DIAGONAL_MM);
const f = focalPxOriginal * (width / srcW);   // 리사이즈 비율 보정
```

설계서 2.1이 명시한 요구사항이다. EXIF에 focal 정보가 없으면 `null`을 보내고, 서버가
4.3 우선순위 4(기본 화각, 신뢰도 0.2)로 떨어진다.

**효과** intrinsics가 있으면 신뢰도 0.95로 quality_score가 약 0.10 오른다.

**적용 위치** `src/lib/image.js`의 `buildIntrinsics`

### FE-10 위치는 촬영 시점에만 확보한다

`getCurrentPosition`으로 한 번 받아 `upload-url` 요청에 실어 보낸다. 서버가 `trucks` 문서의
`current_lat/current_lng`를 갱신한다. 이 값이 Matching M2 경로 회랑의 기준점이 된다.

실패하거나 거부돼도 **업로드는 진행한다.** 위치가 없으면 Matching이 fail-closed로 끝난다.

설계서 1.2의 "30-60초 또는 300-500m 이동 조건 갱신"은 구현하지 않았다. 촬영 시점 1회만이다.

### FE-11 결과 폴링

Vision → Matching 순서로 각각 `GET /v1/results/{photo_id}`를 폴링한다.
처리 중이면 404가 오므로 404는 계속, 그 외 오류는 즉시 중단한다.

- 간격 3초, 타임아웃 180초.
- Vision이 60-105초 걸리므로([VIS-09](04-vision-processor.md#vis-09-성능-특성)) 타임아웃을 줄이지 말 것.

### FE-12 화면이 반드시 지켜야 할 표시 규칙

설계서에서 나온 제약이라 디자인 취향으로 뺄 수 없다. UI를 재생성해도 유지해야 한다.

1. **좌표를 탭시키지 않는다**(2.1). 문틀·벽·화물 경계 지정 UI를 만들지 않는다.
2. **추정치를 실측처럼 보이지 않게 한다**(4.11). `LIMITED` 품질과 `HAVERSINE_FALLBACK` 우회시간을 밝힌다.
3. **가려진 공간이 제외됐음을 알린다**(4.9). `unknown_cbm`을 숨기지 않는다.
4. **`can_load=false`의 이유를 보여준다**(5.8).
5. **정확도를 숫자로 약속하지 않는다**(4.11).
6. **판정에 쓰인 값을 표시한다.** `vision.usable_free_cbm`은 품질 추가 감액 **전** 값이고
   솔버가 실제로 쓴 값은 `matching.usable_free_cbm`이다. 앞의 것을 표에 쓰면
   "사용 가능 공간 − 실은 화물 = 남는 공간"이 맞지 않아 화면 전체를 못 믿게 된다.

### FE-13 찍기 전에 확인시켜야 하는 것 둘

결과가 나온 뒤에 알면 이미 늦는 값이 둘 있다. 둘 다 촬영 버튼 **위**에 둔다.

**차량 제원** — 분석은 등록된 적재함 치수를 자 삼아 사진 속 거리를 미터로 환산한다.
다른 차를 찍으면 결과가 통째로 어긋나는데, 파이프라인은 이걸 오류로 잡지 못한다
([VIS-11](04-vision-processor.md#vis-11-차량-제원이-곧-측정의-자다)). `src/lib/truck.js`가
차량 번호 입력 후 400ms 디바운스로 조회한다.

**현재 위치** — 상차 후보는 트럭 현재 위치 기준 회랑에서 고른다. 위치가 없으면 추천 자체가
중단된다. 예전에는 분석을 시작한 뒤에야 위치를 잡아서 결과가 나온 다음에나 문제를 알 수
있었다. `src/lib/location.js`가 `watchPosition`으로 계속 따라가고, 그 좌표를 그대로
`analyze()`에 넘긴다 — 화면에 보여준 좌표와 분석에 쓴 좌표가 달라지면 안 된다.

지도는 **선택 기능**이다. `KAKAO_JS_KEY`가 주입돼 있으면 카카오 지도를, 없으면 역지오코딩한
주소와 좌표를 보여준다. 키가 없다고 촬영을 막지 않는다.

> JavaScript 키는 길찾기·주소검색에 쓰는 **REST 키와 다른 값**이다. 카카오 개발자 콘솔에서
> 같은 앱의 JavaScript 키를 발급받고 플랫폼 > Web에 프론트 도메인을 등록해야 한다.
> 도메인 제한이 걸린 공개 키라 브라우저에 노출돼도 되고, 그래서 `config.js`로 주입한다
> (REST 키처럼 서버 프록시를 둘 필요가 없다).

### FE-14 숫자만 주지 말고 감산 과정을 준다 (XAI)

"2.72 CBM, 1건 가능"만 보여주면 사용자는 값이 맞는지 확인할 수도, 틀렸을 때 원인을 짚을
수도 없다. `src/lib/explain.js`가 백엔드 값을 **감산 단계 배열**로 늘어놓고, UI는 렌더만 한다.

- 각 단계는 `{label, value, delta, why}` — 이 단계에서 무엇을 얼마나 왜 뺐는지.
- CBM을 모르는 사람을 위해 택배 상자(40×30×30cm) 개수로 환산해 함께 보인다.
- 공간·중량 두 축의 사용률을 나란히 보여, **어느 쪽이 다음 화물을 막았는지**를 짚는다.
  이걸 모르면 사용자는 사진을 다시 찍어야 할지 짐을 덜어야 할지 판단할 수 없다.

`explain.js`는 계산을 새로 하지 않는다. 여기서 CBM을 다시 계산하면 화면과 저장값이 갈라진다.
필요한 중간값은 백엔드가 내려준다([VIS-12](04-vision-processor.md#vis-12-결과에-판정-근거를-함께-싣는다)).

### FE-18 관리자용 적재 배정 화면

화면이 답하는 질문이 하나로 줄었다. **"이 차에 얼마나 실리나."**

그래서 목적지도 운행 중 추적도 없다. 기사가 목적지를 향해 가면서 보는 화면이 아니라,
배차 시점에 관리자가 확인하는 화면이라 필요한 것은 기준 위치뿐이다.

사진 경로도 걷어냈다. 적재된 화물을 0으로 보기로 한 이상 실을 수 있는 공간은 등록 적재함
체적 그 자체라, 사진에서 빈 공간을 추정할 이유가 없다.

| 컴포넌트 | 역할 |
|---|---|
| `ui/CbmHelpCard.jsx` | CBM이 무엇인지. 접어 두고 필요한 사람만 편다 |
| `ui/MyLocationCard.jsx` | 정렬 기준 위치. 주소로 옮길 수 있다 |
| `ui/TruckMatchCard.jsx` | 차량 선택 · 파렛트 여부 · 후보 수 · '매칭 갱신' |
| `ui/MatchSummaryCard.jsx` | 적재율과 요약 표 |
| `ui/CargoFillView.jsx` | 적재함 3D 그림 |
| `ui/ExplainCard.jsx` | 계산 과정(XAI) |
| `ui/TerminalGroupList.jsx` | 출발-도착 묶음 목록 + 구간 필터 |
| `ui/MultiSelect.jsx` | 검색해서 여러 개 고르는 콤보 |
| `lib/useTruckMatch.js` | 매칭 호출. 폴링 없이 응답이 곧 결과 |

`lib/useAnalysis.js`와 `ui/CaptureCard.jsx`는 지우지 않고 남겼다. 되돌릴 때 필요하고,
지운다고 얻는 것도 없다. 어디서도 부르지 않는다.

**수수료·운임·우회시간·손익분기는 화면에서 뺐다.** 그건 기사에게 "갈 만한가"를 묻는
숫자고, 관리자가 배차를 정할 때 보는 것은 물량이다.

### FE-19 자동 갱신을 없앴다

1분마다 재매칭하던 것을 '매칭 갱신' 버튼으로 바꿨다. 주기적으로 다시 돌리면 화면을 보는
사이에 목록이 바뀌어 **방금 판단한 묶음이 사라진다**. 갱신 시점은 사람이 정한다.

대신 화면이 기준 시각을 함께 적는다. 자동으로 갱신되지 않는 화면에서 그 표시가 없으면
지금 보는 숫자가 언제 것인지 알 수 없다.

### FE-20 구간을 고르면 적재율과 그림이 다시 그려진다

출발지·도착지 터미널을 **여러 곳** 고를 수 있고, 고른 조합의 묶음만으로 적재율·적재
그림·건수·무게를 다시 센다. 관리자가 실제로 하는 일이 "어느 구간을 태울지 고르는 것"이라,
고른 결과가 차에 얼마나 차는지 그 자리에서 보여야 한다.

`<select multiple>`을 쓰지 않는다. 여러 개를 고르려면 Ctrl(⌘)을 눌러야 하고 그냥 클릭하면
앞서 고른 것이 통째로 날아가는데, 터미널이 100곳이 넘어 스크롤로 찾는 중에 초기화되면
처음부터 다시 골라야 한다. `MultiSelect`는 클릭 한 번이 곧 토글이고, 코드로도 이름으로도
검색되며, 고른 것은 칩으로 남아 목록을 닫아도 보인다.

고른 조합의 합이 차를 넘을 수 있다. 넘치면 "남는 공간"이 음수가 되는데, 음수를 그대로
보여주면 읽는 사람이 부호를 해석해야 한다. **모자란 양을 그대로 말한다.**

### FE-21 적재율에 따라 색이 변한다

적재율이 오를수록 파랑(HSL 210°)에서 빨강(0°)으로 돈다. 색 하나로 "여유 있다 / 꽉 찼다"가
먼저 읽힌다. 중간에 초록·노랑을 지나 단계로 보이고, 채도와 밝기를 고정해 색이 바뀌어도
상자 세 면의 명암 대비는 유지된다.

**색만으로 판단하게 두지 않는다.** 같은 카드에 퍼센트 숫자가 항상 함께 있다. 적재율 막대와
숫자도 같은 색을 쓴다 — 그림과 숫자가 다른 색이면 서로 다른 것을 가리키는 것처럼 보인다.

### FE-22 적재 그림은 등록 적재함 치수로 격자를 만든다

11톤 윙바디(2.35×9.30×2.45)와 1톤 탑차(1.67×2.83×1.81)는 길이 비가 3배 넘게 차이나는데,
같은 모양 상자에 채우면 그 차이가 그림에서 사라진다. 실제 치수로 칸 수를 정한다.

그리는 순서가 곧 깊이다(화가 알고리즘). **뒤쪽 벽 → 바닥 → 상자 → 앞쪽 벽(반투명)** 순으로
그려야 상자가 적재함 안에 있는 것처럼 보인다. 반투명 벽을 상자보다 먼저 그리면 상자가 차
밖에 붙은 것처럼 뜬다.

**상자 개수는 비율의 표현이지 실제 박스 개수가 아니다.** 운송장 수천 건을 낱개로 그리면
점이 되고, 실제 적재는 3D 빈패킹이라 이 격자와 다르다. 칸 수 대비 채운 칸 수가 적재율과
같아지도록만 맞추고, 그 사실을 그림 밑에 적는다.

### FE-23 XAI는 실제 계산 방식을 따라간다

단계마다 계산 방식을 라벨로 붙인다 — **단순 계산 / 통계 추정 / AI 조합 최적화 / 미사용**.

단순 곱셈까지 AI라고 부르면 정작 판단을 맡긴 부분(조합 최적화)이 묻히고, 결과가 틀렸을 때
무엇을 의심해야 할지 알 수 없게 된다.

솔버가 그리디로 떨어지면 설명도 바뀐다. "이번 계산에는 AI 최적화가 쓰이지 않았습니다"라고
명시한다. 그리디로 계산해 놓고 "AI가 골랐다"고 쓰면 **설명이 아니라 거짓말**이 된다.

차량 제원의 출처(`spec_template_id`)도 함께 적는다. 지금 값은 제조사 공개 제원으로 만든
데이터라, 그 구분이 없으면 시연용 숫자를 근거로 배차하게 된다.
